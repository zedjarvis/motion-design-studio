# Three original product-video workflows

All modes start by inspecting the requested repo with `npm run inspect:repo`.
Read the owning source beyond marketing. Write a claim-to-source evidence map,
the main user journey, audience, one message, dimensions, timing and cue plan.
The agent authors the film; the inspection script is evidence retrieval, not an
autonomous story model. Do not modify the inspected product to make its film.

## Launch or release

Use Brag's rubric: product, supported angle, hook, actual UI, useful duration,
tone, sound, share copy and entry → action → result. Hook → reveal → useful
product moment → CTA normally fits 15–25 seconds. Show the thing instead of
replacing it with a feature list. For a release, inspect the specified diff/tag
and separate newly shipped behavior from pre-existing features. If no release
range is supplied, make a product introduction without invented release claims.

## Feature demo guide

Choose one reachable task and read its actual states, prerequisites and result.
**Feature guides must show the actual product UI.** Use captures/recording of the
running product, or mount its real components with the original styles and
layout. Never redraw a simplified panel, restyle controls, omit navigation or
invent a screen and call it a guide. A source-backed approximation does not pass.

Prefer the actual app with deterministic fictional data through an isolated
demo backend or the product's own browser-test API fixtures. Exercise its real
handlers and capture entry → action → review/confirmation → actual result.
Record the app/build identity, compiled assets, route, viewport, DPR, theme,
locale, demo data policy and source/capture hashes. Retain the native screenshots
or recording as production assets with provenance. Product UI assets are not
artwork benchmark references; this workflow is intentionally demonstrating the
real product. Do not substitute invented markup if the app is unavailable.
Continue investigating a runnable build/component mount or report the access
needed to capture it.

Keep instructional text and motion outside the product viewport. Cursor and
annotations may overlay it, but their coordinates must come from measured real
DOM targets. Do not alter product copy, spacing, colors, fonts or widget states
to fit the video. Use native pixel placement for exact UI acceptance; validate
unobscured sample frames against the captured product pixels. Preserve complete
relevant navigation and state changes. For Schoolbooks, confirmation removes a
finding from Needs attention; History contains Open follow-up task. This must be
observed in the UI, not guessed from the label alone.

Numbered steps, cursor gestures and highlights must synchronize with the native
states. Clearly mark fictional demo values outside the product image. Preserve
error, permission, draft/submission and human-review boundaries. Readability can
justify a longer guide or a deliberate camera crop; a crop must never redesign
or hide a necessary control. Require actual UI provenance and the native UI
pixel checks in addition to normal export checks. See
[the native UI workflow](native-ui.md).

## Social pain-point clip

Derive a plausible pain from implemented behavior, not a made-up statistic or
customer testimonial. Record it as an inference/hypothesis unless the repo
contains evidence of actual user research. Use pain → concrete feature → small
supported outcome → CTA. Frame a portrait composition deliberately; do not just
crop the landscape film. Keep text readable at phone size and leave room for
social player chrome. Never claim the feature performs an action it only drafts.

## Choose visual skills by communicative purpose

- Paint or physical emphasis: `motion-p5-brush`.
- Procedural drawing or explanatory progress: `motion-p5`.
- Agent state: `motion-thinking-orbs`.
- Sketched instruction/callout: `motion-roughjs`.
- Coordinated timing: `motion-animejs`.
- Dense retained graphics/record flow: `motion-pixijs`.

Do not force every library into each film. The acceptance matrix should show
which libraries actually generated visible output, and whether that happened
at build time or per frame. A capability probe is not a product film.

## Sound and delivery

Follow the audio reference for local, licensed music/SFX and optional Kokoro
narration. Original films use original source-backed scripts. Reconstructions
preserve verified reference wording/timing and keep silent references unvoiced.
Narration follows the current brief; do not turn a one-run voice preference into
an unrelated global default. Capture a separate voice track and use held music
ducking across short phrase gaps. Keep attribution with the shareable output.

Register each production, inspect scene and adjacent transition frames, render
through `npm run render`, then run the production export verification. Deliver
MP4, poster, captions/transcript when useful, share copy, credits, source and a
working preview. Record real visual/listening scope in REVIEW.md. Do not label
metadata, an ASR transcript, or muted browser playback a listening review.
